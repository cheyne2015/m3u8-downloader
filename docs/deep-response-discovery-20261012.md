# 深度提取响应识别优化

## 已确认的通用问题

本地真实浏览器测试复现三种漏识别：没有 `.m3u8` 的播放列表接口被地址规则排除；播放器依赖样式加载事件时，拦截样式导致它不初始化；播放列表响应头已到达但正文未完成时，不能及时回传候选。

这些测试使用普通本地页面，不证明此前提供的实际网站已兼容。

## 迅雷扩展代码参考

只读检查本机迅雷扩展 4.1.3 的 `manifest.json`、`assets/background.js-7414d968.js`、`assets/index-f7a6c63b.js`。清单指定所有内嵌页面、document_start；后台通过 `chrome.webRequest.onHeadersReceived` 监听响应头，并存在按内容类型识别媒体的逻辑及播放列表类型集合。部分 M3U8 路径还检查地址是否含 `.m3u8`，不能据此声称迅雷支持所有无扩展名接口。

REA 静态分析证据父记录：`ev_a2db472087e050b4f42c790a4caab580a4657402e4bf7688564517648592256a`。整体语义分析受内存及结果预算限制，覆盖不完整；本文上述结论依据具体代码读取，不代表执行观察。没有复制扩展的压缩代码、下载接管或账号逻辑。

## 实现

- 明确的播放列表内容类型在响应头到达时回传。
- 已完成的 fetch/XHR 普通文本或二进制响应，仅在声明大小不超过 256 KiB、未压缩时检查 `#EXTM3U` 正文开头；每个网页最多检查 32 个不同地址。大响应、压缩响应和缺少长度的响应不做此类正文检查；明确的播放列表类型仍可识别。
- 对确认的候选附加可选协议字段 `verified_playlist` / `verified_urls`，贯穿单次组件、常驻组件及主程序解析。未经确认的地址继续按原规则过滤，签名查询参数原样保留。
- 放行样式，继续限制图片、字体及媒体分片。没有更改浏览器池、任务并发上限或等待预算。
- 保留候选回传数量、有效数量、同等时长备用数量的诊断日志；不新增敏感查询参数输出。

## 验证与交付边界

回归覆盖无扩展名接口、普通文本误报、签名参数保留、三个执行路径、样式初始化、慢正文的提前回传及停止、大响应/错误响应过滤，以及既有动态请求、内嵌页面和四播放器场景。

本次为源码修改。发布使用时需同时重建主程序和独立深度组件；现有 F 盘程序不会因为源码修改而自动更新。

全量回归结果为 746 项通过、1 项失败：旧构建测试要求组件 1.1.1，而构建配置和已安装的清单均为 1.1.2。同步旧断言后，构建配置的 3 项测试全部通过。没有在仅修改该断言后重复整套回归。新增识别测试均在全量回归中通过；源码编译和差异空白检查通过。
