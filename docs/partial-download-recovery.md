# 已下载分片的恢复导出

适用版本：主程序 2.2.3，深度组件继续使用 1.1.3。

## 用户流程

选中父任务后，在右侧失败下载项的右键菜单中选择“更多操作 → 合并已下载片段”。父任务菜单不再重复提供该文件操作。后台读取缓存后，显示完整分片比例、可合并时长和预计缺失时长；未知时长明确显示“未知”。默认取消，只有确认“导出”后才合并。

输出为 `原文件名_内容不完整.mp4`，同名自动追加 `_02` 等序号。结果必须经过 ffmpeg 封装和媒体校验。正常文件不被覆盖，失败或取消不留下伪装成功的输出。成功弹窗支持打开或定位导出文件。

恢复导出不调用任务完成接口：原任务仍保持失败，仍能重试补齐。加密原片段、成功分片以及恢复元数据保留。后续正常下载继续复用缓存，补齐并正常完成后才按原规则清理缓存。

## 实现约束

- 沿用播放列表指纹和保存路径生成缓存任务目录，确认后再次检查可用分片，缓存变化时要求重新预览。
- 只使用已落盘的非空完整分片，不使用 `.part` 文件；保留原始顺序和媒体序号，跳过缺片时不重新编号 AES 的隐式 IV。
- 新缓存保存恢复元数据；Windows 上整个元数据使用当前用户的 DPAPI 加密，包含播放列表信息及已获得的密钥。元数据保存失败不阻断原有下载，但日志说明无法保证离线恢复。
- 旧缓存重新读取播放列表并核对指纹，不重新下载视频分片。不匹配或清单已不可访问时保留缓存并报错，不按目录中文件名盲目拼接。
- 缺少密钥、分段 MP4 初始化信息时只补取这些必要信息；初始化信息沿用原始清单中的缓存编号。无法取得时保留缓存并报错。
- 刷新媒体签名后仍用下载项的原始地址关联恢复信息。
- 导出使用后台工作线程，受下载并发上限约束。暂停、退出或删除任务可以请求取消；被取消的 ffmpeg 导出进程由本次操作回收。
- 不修改任务数据库结构，不自动触发不完整导出，也不将其标记为完整下载。

## 验证范围

`tests/test_partial_download.py` 使用本地 HTTP、合成的普通色块媒体、真实 ffmpeg 和 Qt 界面验证：分片计数、离线预览、可播放导出、只补缺片、AES 序号与密钥、分段 MP4 初始化、同名编号、旧缓存采用、刷新签名的缓存关联、取消/失败清理、确认前缓存变化、排除未完成片段、实际弹窗取消与确认，以及任务状态保留。

恢复文件可能跳过缺失内容、出现音画中断；若剩余数据不能组成可识别媒体，导出会失败并保留缓存。本地回归通过不表示任意来源的损坏媒体均可恢复。

2026-10-19 验证：专项覆盖 11 个用例，全量回归 758 项通过。首次全量运行在旧界面测试的 `tcl86t.dll` 中以 `0x80000003` 退出；保存完整日志后重跑通过，尚未证明该间歇性测试退出的触发原因。正式构建使用 Qt 并排除 Tk。候选 EXE 构建、模块打包检查和启动通过；Windows 原生界面的右键操作验证因用户按 Esc 停止，未完成。上述成功导出和确认/取消行为已在真实 Qt 测试及真实 ffmpeg 中验证，不能替代尚未完成的原生操作记录。

主要修改文件：`downloader.py`、`partial_download.py`、`downloader_adapter_v2.py`、`tasking/download_coordinator.py`、`background_v2.py`、`gui_v2.py`，以及上述测试、适配测试、README 和程序版本号。
